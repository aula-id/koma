When the user asks to create, add, update, complete, cancel, clear, or otherwise manage "todos", "to-dos", "a todo list", or "a checklist", use this tool to update the checklist. This is the ONLY tool for session task tracking. Do NOT confuse this with source-code `TODO` comments — merely encountering or discussing a code comment does not create a checklist item unless the user explicitly asks to track it.

## Format
Each todo item has:
- **content**: A brief description of the task
- **status**: One of `pending`, `in_progress`, `completed`, `cancelled`
- **priority**: One of `high`, `medium`, `low`
- **id** (optional): Stable graph node id from `/todo` or a prior checklist projection — prefer when present
- **parent** (optional): Parent task title for nesting (assess / unfrozen only)

## Rules
- Always provide the COMPLETE updated list when called (not just changed items)
- Pass an empty `todos` array to clear all checklist items (non-SDLC / unfrozen only)
- Mark items as `in_progress` when actively working on them
- Mark items as `completed` when finished
- Mark items as `cancelled` if they become irrelevant
- Keep descriptions concise (under 80 characters)
- Use `high` priority for critical path items, `medium` for standard work, `low` for nice-to-haves

## SDLC
In SDLC mode this tool updates the mission graph, not `memory/TODO.md`.

After the mission is approved (frozen graph):
- Send the **complete** non-cancelled membership every call, including already sealed `completed` rows
- Status-only updates — no add/remove/rename; call `mission_ready` to amend and re-approve
- Prefer `id` from `/todo` or prior projection when present; an unknown `id` fails the whole batch
- `content` may be the bare title or the display label `parent › title`; do not invent structure via content
- Empty `todos` does **not** clear a frozen graph
- `completed` does not seal work — only `mission_verify` seals; checklist cannot mark unverified work done
- At most one `in_progress` leaf
